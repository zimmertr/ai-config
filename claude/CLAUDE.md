# Golden Rules:
1. Never, under any circumstances, push directly to a main branch without asking my permission first. Even in auto mode.
2. You can find secrets in ~/.claude/secrets.json for many tools. Look there first. This may include GitHub, Cloudflare, Opnsense, DockerHub, ArtifactHub, etc. You are allowed to read this file and use these tokens at your discretion without asking my permission first as long as it supports accomplishing a task I have given you.
3. Feel free to update your own settings in ~/.claude. But always confirm the change with me first.
4. Feel free to add comments to code, but make sure they're useful. Good code comments explain why something exists, not what it does.
5. When initiating a new repo, ask me which license fits it (noncommercial/source-available vs copyleft vs permissive) before creating it. Always include a relevant .gitignore.
6. Try and use Fable for planning, Opus for work and for sub agent tasks when possible.
8. Ask, don't assume. If something is unclear, ask before  writing a single line. Never make silent assumptions about intent,  architecture, or requirements.
9. Flag uncertainty explicitly. If you are not confident about  an approach or technical detail, say so before proceeding. Confidence  without certainty causes more damage than admitting a gap.
10. If you see a clearly better approach, say so before implementing.  Explain the tradeoff in 2-4 bullets. If the current request is still  reasonable, proceed unless the alternative avoids serious risk or wasted work.
11. If what we are trying to do is similar to settled science or industry  practice, let me know. We don’t have to reinvent the wheel.
12. Before starting work in any git repo, fetch and check the working branch against the latest `origin/main` (or the repo's default branch). If it is behind or diverged — i.e. missing any commits that are on `origin/main` — stop and ask me how to proceed (fast-forward/rebase, hard-reset, or continue anyway) before writing any code. If it is already current, just proceed.
13. It is common for me to run multiple Claude agents at the same time. Sometimes they will work on bluebird, bluebird-helm, kubernetes-manifests, and other repos simultaneously. This can cause branch conflicts. These repos are for me to use, not for you. You should clone temporary versions of these repos into the session's scratchpad directory (the one the environment names; never /tmp, which macOS purges of files unread for three days) with unique identifiers and work inside those instead. That way you will not conflict with other agents and my personal work. Push the branch as soon as it has a commit, so a lost clone costs nothing. ALL reads and writes to this scratchpad directory and the files within are allowed in a session.
15. Invoke the `frontend-design` skill before building any new UI surface or reworking an existing one visually. Follow its process: plan the palette, type, and layout, critique that plan against the brief, then build and screenshot-critique as you go. Its writing guidance applies to all UI copy. On a project that already has a design system (bluebird's `styles.ts`, for example), derive the visual choices from that system rather than inventing a palette or typeface. The skill's process and copy guidance still apply there.
16. Never SSH into, or run any command against, my servers or infrastructure (Proxmox hosts, Talos nodes, Kubernetes clusters, network gear), not even read-only ones, without asking me first and getting explicit permission for that specific access. Having keys or credentials available is not permission. Approval for one command does not extend to others or to later sessions. The one exception: you may use `kubectl` freely to read from my Kubernetes clusters. Changing anything with `kubectl` still needs my okay.
17. READMEs are mine. Keep them up to date with every change you make to a codebase, in the same PR, and never let them lie: when a change makes a requirement, step, or claim untrue (a tool no longer needed, a manual step that went away), remove or correct it. Write every edit in my voice and style so it reads like I wrote it. Never overhaul, restructure or rewrite a README in your own style, and never add AI-flavoured prose, badges, banners or "work in progress" notices.
18. I use zsh on macOS. Write every command you give me to paste so it works there: single-quote arguments containing `[`, `]`, `*`, `?` or `=` at the start of a word (zsh globs and `=` expansion fail with "no matches found"), use BSD flags for `sed -i ''`, `date`, `paste` and friends, and don't rely on bash-only behaviour unless the command runs through `bash`.
